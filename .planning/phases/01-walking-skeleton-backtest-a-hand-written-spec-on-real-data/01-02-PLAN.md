**Every field on every new model gets an explicit `@map("snake_case_name")`.** Prisma does NOT
translate camelCase field names into snake_case columns — the existing schema proves it, using
`@@map` for table names only (`schema.prisma:24`, `schema.prisma:43`) while fields like
`emailVerified` and `accessTokenExpiresAt` stay camelCase in Postgres. Without field-level `@map`,
Prisma emits quoted camelCase columns, and every hand-declared snake_case SQLAlchemy Core column in
Task 3 binds to a column that does not exist. The intended SQL contract for this project is
snake_case, so the fix is the explicit `@map` on each field rather than renaming the Core columns —
that keeps the Prisma models idiomatic on the TypeScript side and the physical schema idiomatic on
the SQL side. Do not add `@map` to the four carried-over better-auth models: Better Auth resolves
its own columns by the names it already created, and renaming them is a Phase 4 concern.

Add three new models.

`Trial` maps to `@@map("trials")` and carries the five VALID-01 fields plus the D-15 outcome:
`strategyLineageId String @map("strategy_lineage_id")`, `paramsHash String @map("params_hash")`,
`objective String`, `ranAt DateTime @default(now()) @map("ran_at")`,
`wasOos Boolean @map("was_oos")`, `status String`, and
`errorMessage String? @map("error_message")` for the crash text. The `status` column is what makes
a failed experiment counted rather than inferred. Index `@@index([strategyLineageId])` and
`@@index([paramsHash])` following the existing file's `@@index` convention.

`SnapshotCapture` maps to `@@map("snapshot_capture")` and is the parent identity of one daily
capture: `captureDate DateTime @db.Date @map("capture_date")` (the UTC calendar date the capture is
*for*), `capturedAt DateTime @map("captured_at")` (the single wall-clock instant every child row in
this capture shares), `payloadSha256 String @map("payload_sha256")`,
`expectedSymbolCount Int @map("expected_symbol_count")`,
`actualSymbolCount Int @map("actual_symbol_count")`, `status String` (`started`, `complete`,
`failed`), and `symbols SymbolListingSnapshot[]`. Index `@@index([captureDate])`.

`SymbolListingSnapshot` maps to `@@map("symbol_listing_snapshot")` and carries, per D-13,
`rawPayload Bytes @map("raw_payload")` for the gzip-compressed exchangeInfo response plus the
extracted columns `symbol String`, `status String`, `baseAsset String @map("base_asset")`,
`quoteAsset String @map("quote_asset")`,
`tickSize Decimal @db.Decimal(38,18) @map("tick_size")`,
`stepSize Decimal @db.Decimal(38,18) @map("step_size")`,
`minNotional Decimal? @db.Decimal(38,18) @map("min_notional")`,
`capturedAt DateTime @map("captured_at")`, and the parent link
`captureId String @db.Uuid @map("capture_id")` with
`capture SnapshotCapture @relation(fields: [captureId], references: [id], onDelete: Cascade)`.
Index `@@index([capturedAt])`, `@@index([symbol, capturedAt])` and `@@index([captureId])`.
`minNotional` is nullable because a symbol whose filter list omits that filter is information, not
an error — the extractor records the absence rather than dropping the symbol.

The parent row exists because counting child rows proves activity, not completeness. Success
criterion 4 asserts *one complete capture per day with no gaps*, and a per-symbol-only table cannot
distinguish a finished capture from a half-written one, cannot detect that yesterday's capture
carried 400 symbols where today's carried 12, and lets a retry double every symbol row for a day
with nothing marking which set is the real one. With the parent, the gapless query reads
`SELECT capture_date FROM snapshot_capture WHERE status = 'complete' ORDER BY capture_date` and a
missing date means a dead cron rather than an unchanged universe.

The ID default on all three new models must be
`@id @default(dbgenerated("gen_random_uuid()")) @db.Uuid` and NOT the `@default(uuid())` pattern the
four existing models use. This is a deliberate deviation, not an oversight: the existing pattern
generates the value inside the Prisma client, so Postgres gets no DEFAULT clause and a bare
SQLAlchemy Core INSERT that omits the key violates the NOT NULL constraint. Say so in a comment
above each new model and in `prisma/README.md` so a reviewer does not "fix" it back to match the
other four. `@default(now())` on `ranAt` does compile to a real SQL `DEFAULT CURRENT_TIMESTAMP`, so
that column can safely be omitted from the Python INSERT. `capturedAt` deliberately carries no
default on either snapshot model — the writer passes one explicit instant for the whole batch, so a
capture's rows cannot drift across a per-statement clock read.

Do NOT add a unique constraint on `(symbol, capturedAt)`, on `captureDate`, or on any
date-truncated column, and do NOT add `validFrom`/`validTo`. D-14 requires one row per symbol per
day written unconditionally, even when byte-identical to the previous day, because a deduplicated
table cannot distinguish "the universe did not change" from "the cron silently died" — which is
exactly what success criterion 4's gapless daily count exists to prove. The same reasoning applies
to the parent: a unique constraint on `captureDate` would make a retry *fail* rather than *be
visible*, so two complete captures for one date are recorded and surfaced by the query rather than
blocked at write time.

Leave `apps/server/prisma/` on disk untouched; it is out of the workspace per D-09 and Phase 4 will
reconcile it. Record that reconciliation burden explicitly in `prisma/README.md` — after this task
the repository holds two Prisma schemas that will diverge: this one gains the three quant tables
and snake_case `@map` directives, while `apps/server/prisma/schema.prisma` keeps the four
better-auth models and the CDK/Hono/Better-Auth runtime built around them. Name both paths, say
which is authoritative for Phase 1, and say that Phase 4 must merge them rather than pick one, so
the divergence is a tracked decision and not a surprise.
