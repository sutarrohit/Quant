Harden the pure evaluator's edge semantics and make the purity boundary a CI gate rather than a
convention.

Purpose: success criterion 3 has two halves and only one of them is a grep. The other half —
"the evaluator suite runs against a plain list of bars in under a second with no engine present" —
is not provable by a test that merely avoids importing the engine while the package sits importable
in the same environment. That proves avoidance. Proving absence needs a separate environment where
the package genuinely is not installed, and that is a CI job, not a test.

regresses.
</objective>

  <behavior>
    - Test 1 (adjacency): when the fast and slow averages are exactly equal on a bar, no signal is emitted; a signal requires a strict sign change of `fast - slow` between the previous bar and the current one.
    - Test 2 (adjacency): a sequence that touches equality and returns to the same side emits no signal at all — touching is not crossing.
    - Test 3 (adjacency): a sequence that touches equality and continues through to the other side emits exactly one signal, on the bar where the sign genuinely changed.
    - Test 4 (empty): an empty bar list yields an empty signal sequence and raises nothing.
    - Test 5 (empty): a single bar yields no signal.
    - Test 6 (empty): fewer bars than the slow window yields no signal and raises nothing — the warmup period is silent, not an error.
    - Test 7 (empty): the bar exactly at the slow-window length is the first bar that may produce a signal.
    - Test 8 (ordering): signals come back in bar-timestamp order for an ascending input.
    - Test 9 (ordering): two bars sharing an event timestamp are processed in input-list order, and repeating the run yields the identical sequence.
    - Test 10 (concurrency): two evaluator instances built from the same spec, fed the same bars interleaved bar-by-bar, produce identical signal sequences.
    - Test 11 (no lookahead): an evaluator fed bars one at a time produces the same sequence as one fed the whole list, proving no decision depends on a bar not yet delivered.
    - Test 12 (determinism of arithmetic): all moving-average arithmetic is `Decimal`; the suite asserts no intermediate value is a float.
  </behavior>
  <action>
Define the crossover rule as a strict sign change of `fast - slow` between the previous evaluated
bar and the current one. Equality emits nothing, on either the entry or the exit side. This is the
only defensible reading: a moving-average pair that touches and bounces back has not crossed, and
treating equality as a cross makes the strategy fire on a condition that is an artifact of decimal
scale rather than of price. Store the previous comparison's sign, not the previous averages, so the
rule is expressed once and cannot drift between the entry and exit branches.

Define the warmup period explicitly: until the evaluator has seen as many bars as the slow window,
it emits nothing and raises nothing. An empty list, a single bar, and a short list are all the
silent case. The first bar that may produce a signal is the one at exactly the slow-window length.

Hold all state on the instance — a bounded deque of closes plus the previous sign — and nothing at
module or class level. Two evaluators built from the same spec must not be able to influence each
other, which is what makes the evaluator safe to run in the same process as another and what
Test 10 pins down.

Keep every arithmetic value a `Decimal` throughout. The moving average of decimal closes is a
decimal division, and dividing through a float for convenience would put a float on a price path
in the one module the whole architecture exists to keep clean.

The evaluator continues to import only the standard library, `engine.dsl.spec` and `engine.money`.
No comment or docstring under `engine/dsl/` may name the trading engine's module: the purity gate
is a bare recursive content grep over this directory, so a mention in prose would make the gate
report a violation that does not exist. The explanation belongs in `engine/README.md`, which is
outside the grepped path — Task 2 writes it there.

Do not extend the DSL. D-26 bounds the Phase 1 surface to exactly what the crossover spec needs,
and CONTEXT.md records the developer considering a second structurally different spec and dropping
it. This task defines edges on the existing surface; it does not add expressiveness.
  </action>

Write `engine/tests/dsl/test_purity_boundary.py` with two assertions. First, the literal recursive
content grep over the pure directory returns no files. Second, the count of non-test modules under
the engine tree that import the trading engine is exactly one, and that one is the adapter. The
second assertion is what keeps `SIM-04` structurally true: the same evaluator code path runs in
backtest, paper and live only because there is one adapter file to swap, and a second dual-import
file would quietly end that property without breaking any behaviour test.

Use the literal grep, not an import-boundary linter. Success criterion 3 *is* the grep, so a
second differently-shaped check would drift from what the roadmap promises, and it would add a
dependency whose only job is to restate an acceptance criterion that already exists.

Write `.github/workflows/dsl-purity.yml`: a job that creates a virtual environment from the engine
project **excluding** the vendored engine path dependency, asserts that importing the trading
engine raises a module-not-found error, and then runs only the pure suite with a wall-clock timeout

demonstrates avoidance; only an environment where the package genuinely is not installed
demonstrates absence, and absence is what the criterion claims. The job also runs the grep, so a
regression fails CI even if someone deletes the in-suite assertion.

Do not build the vendored engine in this job. Excluding it is the entire point, and it also makes
this the fastest job in CI — which matters, because a purity gate that takes as long as the Rust
build is a purity gate someone will eventually make non-blocking.

Write `engine/README.md` stating the boundary rule in prose: the pure directory may not import the
trading engine, the adapter is the only file that may import both, the enforcement is the literal
grep in the workflow, and — critically — no comment or docstring inside the pure directory may name
the forbidden module, because the gate is a bare content grep and prose about the rule would trip
it. This README is outside the grepped path, which is exactly why the explanation lives here.

Review `engine/adapters/dsl_strategy.py` and move any decision logic that leaked into it back into
the evaluator. The adapter translates and acts; it does not decide. Anything in it that reads a
