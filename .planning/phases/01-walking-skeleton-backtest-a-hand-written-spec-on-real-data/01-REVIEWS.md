# Cross-AI Plan Review — Phase 1

## Codex Review

## Summary

The plans show strong architectural discipline around the pure DSL seam, checksum-first ingestion, non-backfillable histories, and deterministic serialization. However, several implementation assumptions are incorrect or mutually incompatible. In their current form, the plans are unlikely to execute cleanly or satisfy all six phase criteria. The most serious blockers are incorrect Prisma column mapping, an impossible “only one Nautilus-importing module” invariant, a broken fresh-clone code-generation dependency, and a mismatch between “byte-identical output” and merely equal canonical hashes. The phase is also considerably thicker than a walking skeleton: full-history multi-symbol S3 ingestion, hosted Postgres, Secrets Manager, multiple workflows, devcontainers, extensive ADRs, and roughly 70+ planned tests create a large critical surface before the basic spine is proven.

## Strengths

- The source-derived restructuring assumptions are accurate. The root package is still named `template`, and the root scripts already delegate to Turbo as claimed ([package.json:2](/Users/criox4/Codes/Trade_Platform/quant-platform/package.json:2), [package.json:5](/Users/criox4/Codes/Trade_Platform/quant-platform/package.json:5)). The workspace currently includes `apps/*` and `packages/*`, matching Plan 01-01’s starting point ([pnpm-workspace.yaml:1](/Users/criox4/Codes/Trade_Platform/quant-platform/pnpm-workspace.yaml:1)).

- The decision to reuse the existing Turbo task graph is sound. `build`, `lint`, `check-types`, and `test` are already package-agnostic tasks, and tests already depend on upstream builds ([turbo.json:5](/Users/criox4/Codes/Trade_Platform/quant-platform/turbo.json:5), [turbo.json:33](/Users/criox4/Codes/Trade_Platform/quant-platform/turbo.json:33)).

- Plan 01-01 correctly identifies substantial template code that must be removed. The FastAPI package really does contain JWT authentication, SQLite, Alembic, users, and posts rather than a neutral supervisor shell ([pyproject.toml:8](/Users/criox4/Codes/Trade_Platform/quant-platform/packages/fastapi-server/pyproject.toml:8), [main.py:11](/Users/criox4/Codes/Trade_Platform/quant-platform/packages/fastapi-server/main.py:11), [auth.py:4](/Users/criox4/Codes/Trade_Platform/quant-platform/packages/fastapi-server/auth.py:4)).

- The Prisma extraction is based on real source structure. The existing schema has the four Better Auth models and client-side `uuid()` defaults exactly as described ([schema.prisma:11](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:11), [schema.prisma:27](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:27), [schema.prisma:43](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:43), [schema.prisma:63](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:63)).

- Moving database-side UUID generation into Postgres is appropriate for SQLAlchemy writers. The current schema’s IDs are generated by Prisma Client, so Python inserts that omit IDs would indeed need database defaults or client-generated UUIDs.

- Checksum failure, safe ZIP handling, timestamp-unit fixtures, close-time assertions, and “no partial catalog write” are well-designed ingestion controls. These directly address silent data corruption rather than treating ingestion as a simple download script.

- The evaluator boundary is designed around a plain `PlainBar`, instance-local state, Decimal arithmetic, explicit warmup, equality semantics, and no-lookahead tests. That is a strong foundation for later reuse across backtest, paper, and live adapters.

- The snapshot is scheduled early enough in dependency terms: Plan 01-06 depends only on Plan 01-02 and can begin alongside the tracer. This appropriately overlaps the elapsed-days requirement with later implementation work.

- The plans recognize that raw Parquet bytes are unsuitable as a semantic determinism hash and explicitly exclude process-specific metadata. That is the correct direction for reproducibility, even though the success criterion needs clarification.

## Concerns

- **HIGH — Prisma physical column naming is wrong.** Plan 01-02 states that Prisma “maps camelCase field names to snake_case columns implicitly” ([01-02-PLAN.md:291](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-02-PLAN.md:291)). It does not. Without field-level `@map("strategy_lineage_id")`, Prisma will create quoted camelCase columns such as `strategyLineageId`. The proposed SQLAlchemy tables use snake_case names, so inserts and schema-parity tests will fail. The existing schema demonstrates that only table names have explicit `@@map` directives; fields remain camelCase ([schema.prisma:12](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:12), [schema.prisma:24](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma/schema.prisma:24)).

- **HIGH — the Prisma configuration paths are probably copied at the wrong directory depth.** The current config resides at `apps/server/prisma.config.ts` and therefore correctly points down to `prisma/schema.prisma` ([prisma.config.ts:10](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/prisma.config.ts:10)). Plan 01-02 moves the config inside the new `prisma/` directory but preserves `schema: "prisma/schema.prisma"` ([01-02-PLAN.md:146](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-02-PLAN.md:146)). Depending on Prisma’s resolution base, that may resolve as `prisma/prisma/schema.prisma`. This needs a deliberate CLI probe before being encoded as an instruction.

- **HIGH — the Nautilus import invariant is incompatible with the planned architecture.** Plan 01-05 requires exactly one non-test module under `engine/` to import Nautilus ([01-05-PLAN.md:287](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-05-PLAN.md:287)). Yet `engine/data/catalog.py` must use `ParquetDataCatalog`, `engine/data/binance_vision.py` must construct Nautilus bars, and `engine/cli/backtest.py` must configure `BacktestNode` and obtain reports. Those modules necessarily need Nautilus imports unless all engine-facing operations are artificially re-exported through the adapter. FOUND-06 only requires `DslStrategy` to be the sole file importing both the evaluator and Nautilus—not the sole Nautilus importer in the whole engine.

- **HIGH — fresh-clone code generation is not wired into the dependency graph.** Generated Pydantic code is gitignored, but `engine/dsl/spec.py` imports it. The engine build script is only `uv sync --frozen` ([01-01-PLAN.md:270](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-01-PLAN.md:270)); it does not generate models. Unless `@repo/engine` declares an explicit workspace dependency on `@repo/schemas` and Turbo sees that edge, `test`’s `^build` dependency will not guarantee schema generation. A clean checkout can therefore fail before tests collect.

- **HIGH — the strict Decimal contract is internally inconsistent.** Plan 01-04 requires `Money` to use `ConfigDict(strict=True)` while also requiring Python-mode construction from a decimal string to succeed ([01-04-PLAN.md:275](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-04-PLAN.md:275), [01-04-PLAN.md:284](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-04-PLAN.md:284)). Strict Decimal validation generally accepts actual `Decimal` objects in Python mode, not arbitrary strings. The design should distinguish wire parsing (`model_validate_json` or an explicit string parser) from strict internal construction.

- **HIGH — standard JSON Schema cannot directly express `fast_period < slow_period`.** Plan 01-04 demands this as a schema constraint. Draft 2020-12 handles constraints on individual values but has no portable cross-property comparison keyword. This must be implemented as a semantic validation step or a generated Pydantic model validator. Otherwise the stated acceptance test cannot pass using the schema alone.

- **HIGH — FOUND-01 is not actually satisfied.** FOUND-01 says a stock v2 `LiveNode` runs. Plan 01-03 verifies only that the package imports and reports `2.0.0rc4`; it explicitly defers actual `LiveNode` usage. An import test proves pinning, not that a clean v2 node starts. Either reduce FOUND-01’s Phase 1 interpretation in the requirement or add a minimal node-construction/startup smoke test.

- **HIGH — “byte-identical output” has been weakened to “equal hash over selected data.”** The phase goal says output is byte-identical across machines, while Plans 01-05 and 01-09 intentionally allow Parquet bytes to differ and compare only `hash.txt`. That is a defensible semantic reproducibility contract, but it is not literal byte-identical output. Either redefine the success criterion as byte-identical canonical payload/hash or make the artifacts deterministic too.

- **HIGH — run artifact requirements contradict `--plot`.** Plan 01-09 says `--plot` creates a PNG in the run path but also asserts that the output directory contains exactly the three D-19 artifacts. A plotted run necessarily has a fourth file unless the PNG is written elsewhere. The acceptance criterion needs separate cases for plotted and unplotted runs.

- **MEDIUM — snapshot identity and gap semantics are under-modeled.** The design inserts one row per symbol per run, not one snapshot per day ([01-06-PLAN.md:46](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-06-PLAN.md:46)). Retries can create duplicate daily symbol rows, partial symbol sets need detection, and DB-generated `captured_at` values may differ slightly across a batch. Counting rows or grouping by date proves activity, but not exactly one complete capture per day. A parent `snapshot_run` record with capture date, payload hash, symbol count, and completion status would make gap and completeness checks reliable.

- **MEDIUM — the trials guarantee is weaker than its language.** “Every invocation path” is hard to guarantee with a completion-time context manager. Failures during argument parsing, spec loading, database connection setup, or process startup may occur before the recorder exists. Additionally, objective is only known after the run, making the proposed context-manager API underspecified. The deliberate SIGKILL ceiling is documented, but ordinary pre-engine failure paths also need classification.

- **MEDIUM — snapshot dependency isolation is not designed concretely.** Plan 01-06 requires a daily workflow that installs only the snapshot subset while the main engine project has an editable Nautilus dependency ([01-06-PLAN.md:274](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-06-PLAN.md:274)). No exact uv dependency-group or packaging mechanism is specified. An “explicit package list” risks drifting from the lockfile, while syncing the project risks compiling Nautilus.

- **MEDIUM — the scheduled-workflow verification is brittle.** `gh workflow run && sleep 90` assumes GitHub has discovered the workflow, that the branch containing it is available remotely, and that the run completes within 90 seconds ([01-06-PLAN.md:301](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-06-PLAN.md:301)). It can also inspect an older run. Poll by returned run ID with a bounded timeout.

- **MEDIUM — the archive-tag verification checks only a local tag.** Plan 01-03 claims preservation on the fork but verifies only `git tag -l` inside the submodule ([01-03-PLAN.md:275](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-03-PLAN.md:275)). A local tag can disappear with the machine. Verify the remote ref after pushing.

- **MEDIUM — touching a Rust source file violates the clean-submodule invariant unless restoration is explicit.** Plan 01-03 asks for a one-line-touch rebuild ([01-03-PLAN.md:240](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-03-PLAN.md:240)) and later requires a clean submodule. The task should specify an exact reversible edit and restoration, followed by the cleanliness assertion.

- **MEDIUM — the phase is too thick for its stated tracer-first purpose.** Plan 01-07 expands immediately to full history, four symbols, object storage, read-through caching, resumable ledgers, and live AWS round trips ([01-07-PLAN.md:227](/Users/criox4/Codes/Trade_Platform/quant-platform/.planning/phases/01-walking-skeleton-backtest-a-hand-written-spec-on-real-data/01-07-PLAN.md:227)). This adds substantial operational risk without being necessary to demonstrate one deterministic BTCUSDT backtest. It also conflicts with the context’s statement that “breadth arrives when Phase 3 needs it.”

- **LOW — the existing apps contain more coupled infrastructure than “leave untouched” suggests.** The server package includes Prisma, CDK, Hono, Better Auth, and runtime scripts ([apps/server/package.json:21](/Users/criox4/Codes/Trade_Platform/quant-platform/apps/server/package.json:21)). Delisting it is fine, but copying only the Prisma schema and then leaving two divergent schema copies creates a future reconciliation burden that should be explicitly tracked. *(Review text left as written. The CDK half is no longer true: `aws-cdk-lib`, `infra/`, `lambda/` and the `cdk:*` scripts have since been removed from `apps/server`.)*

## Suggestions

- Correct every new Prisma field with explicit `@map`, for example `strategyLineageId String @map("strategy_lineage_id")`, or make SQLAlchemy use the actual camelCase column names. Prefer explicit maps because the desired SQL contract is already snake_case.

- Run a small Prisma probe before execution to confirm config-relative path behavior and emitted migration SQL. Set `schema` and migration paths based on that evidence.

- Replace the impossible Nautilus invariant with two checks:

  - `engine/dsl/` contains no Nautilus imports or text matches.
  - Exactly one module imports both `engine.dsl.evaluator` and Nautilus, and that module is `engine/adapters/dsl_strategy.py`.

- Make code generation a real build dependency. Either commit generated models, or add an explicit `@repo/engine -> @repo/schemas` workspace dependency and ensure the engine build invokes or depends on schema generation before import/test.

- Separate wire and internal money handling: accept only decimal strings at JSON/schema boundaries, parse explicitly to `Decimal`, and require actual `Decimal` internally. Test both boundary modes instead of expecting one strict Pydantic model to accept both.

- Move `fast_period < slow_period` into a semantic `StrategySpec` validator and describe it honestly as semantic validation, not JSON Schema validation.

- Add a minimal `LiveNode.builder(...)` smoke test if FOUND-01 remains assigned to Phase 1. If starting a node requires live infrastructure, narrow FOUND-01’s wording for this phase and map actual startup to Phase 5.

- Amend success criterion 2 to say “byte-identical canonical result bytes and hash,” or pin Parquet writer versions and normalize metadata if literal artifact-byte equality is truly required.

- Introduce a `snapshot_capture` parent table keyed by UTC capture date. Write one parent row and its symbol children transactionally, then mark the capture complete with expected/actual symbol counts. This makes daily gap detection, retry behavior, and partial-write detection precise.

- Start the snapshot deployment immediately after Plan 01-02, operationally—not merely in the same numbered wave. Treat provider setup as a day-zero checkpoint so human setup cannot silently defer the non-backfillable history.

- Reduce Phase 1 breadth. Keep the tracer, daily snapshots, honest trials, timestamp-boundary tests, and two-machine determinism. Defer S3 read-through caching and four-symbol full-history ingestion until a later data-expansion plan unless they are essential to the acceptance test.

- Define trials lifecycle explicitly: insert a `started` row once inputs identify a valid run, update it to `completed`, `crashed`, or `aborted`, and document whether invalid CLI invocations count. If write-ahead is intentionally deferred, weaken “every invocation path” to the exact set the implementation can guarantee.

- Replace fixed sleeps in workflow verification with run-ID polling, and verify remote Git refs rather than local tags.

## Risk Assessment

**Overall risk: HIGH.**

The architecture is directionally strong, but four issues are execution blockers: Prisma column mismatch, incompatible Nautilus import assertions, missing codegen dependency wiring, and the strict-Decimal contradiction. Separately, the plans do not literally satisfy the `LiveNode` or byte-identical-output criteria as written. Correcting those items and trimming the full-history/S3 expansion would lower the phase to medium risk while preserving its core trust argument.

## Summary

The Phase 1 implementation plans for the Trade Platform's walking skeleton are exceptionally detailed and well-structured, covering all 14 requirements for this phase through 9 interconnected plans. The plans correctly implement a phased approach with clear dependencies, addressing the core architectural decisions outlined in the context (D-01 through D-26). ## Strengths

- **Clear dependency management**: Plans have logical dependencies (e.g., 01-05 depends on 01-02, 01-03, 01-04) ensuring foundational elements are in place before the tracer
- **Non-backfillable histories prioritized**: Plans 01-02 (Prisma/Postgres setup) and 01-06 (daily snapshot cron) correctly implement DATA-03 and VALID-01 requirements early enough for the waiting period to overlap with other work
- **Determinism enforcement**: Plans 01-05 (tracer) and 01-09 (two-machine verification) properly address success criterion 2 with canonicalization and exclusion of process-specific fields
- **Purity boundary enforcement**: Plan 01-08 correctly implements both halves of success criterion 3 through grep checks and CI jobs that verify absence of engine in pure directories
- **Security considerations**: Proper handling of credentials via secrets manager (D-16) and attention to SQL injection prevention through parameterized queries
- **Realistic scope management**: The tracer plan (01-05) correctly limits scope to one symbol, one month, and a simple SMA crossover strategy as intended
- **Clear separation of concerns**: Well-defined layers (ingestion, catalog, DSL evaluator, adapter, CLI) with clear interfaces

## Concerns

- **HIGH**: The plans assume the existence of a Rust toolchain and maturin for the Nautilus submodule editable install, but don't explicitly verify this in early setup tasks (01-03 does check this, but it's a blocking human task)
- **HIGH**: Plan 01-06's dependency on a hosted Postgres provider introduces external reliability risks; while the local dev Postgres is provided, the production snapshot depends on external services
- **MEDIUM**: Plan 01-04's decision spike for JSON Schema to Decimal conversion could delay progress if the spike reveals complexity not anticipated in the plan
- **MEDIUM**: The plans don't explicitly address how the team will handle potential conflicts between the local development Postgres and the hosted snapshot Postgres in terms of schema migrations
- **LOW**: Some plans (like 01-07) assume AWS S3 for object storage without evaluating alternatives that might be simpler for initial development
- **LOW**: The plans don't explicitly mention how they'll handle the case where the Nautilus submodule URL or fork becomes unavailable

## Suggestions

- Add explicit verification of Rust toolchain availability in plan 01-01 or early in 01-03 before attempting the submodule checkout
- Consider adding a fallback mechanism or clearer documentation for the hosted Postgres dependency in plan 01-06, including testing procedures
- Add timeboxing to the decision spike in plan 01-04 to prevent open-ended investigation
- Clarify the relationship between local and hosted Postgres instances in the documentation, particularly regarding schema evolution
- Consider evaluating simpler storage options for initial development in plan 01-07 (like local disk with clear upgrade path to S3)
- Add verification steps for the Nautilus submodule URL validity before attempting to add it as a submodule

**Overall Risk Level: MEDIUM**

Justification: While the plans are thorough and address all requirements with appropriate risk mitigations (like the human checkpoints for package legitimacy and engine legitimacy), there are several medium-risk items that could impact the timeline:
