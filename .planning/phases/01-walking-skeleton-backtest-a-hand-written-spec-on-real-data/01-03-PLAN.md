<objective>
Vendor NautilusTrader v2 as a commit-pinned git submodule installed editable, measure the cold
Rust rebuild time and record the number, pin the development environment, and write the tenancy
archive record.

Purpose: `FOUND-01` requires a stock engine at a pinned upstream commit with no local patches, and
D-04 chose a submodule over a wheel precisely so that PROJECT.md's tripwire 3 — "how long does a
Rust rebuild take" — becomes measurable instead of theoretical. RESEARCH.md's Pitfall 4 is blunt
about the sequencing risk: any plan that puts adapter work on the critical path without first
measuring the build is guessing about its own iteration speed. This plan takes the measurement
before the tracer is written.
Output: `vendor/nautilus_trader` at a pinned commit, an editable install that imports, a recorded
rebuild-time baseline, a pinned devcontainer, and two ADRs.
</objective>

  <action>
Take three timed measurements against the vendored workspace and record the actual numbers:

1. **Cold build** — with the workspace's build directory removed and the cargo registry cache
   present, time the submodule's debug build target end to end.
2. **Warm no-op rebuild** — run the same target again immediately, changing nothing.
3. **Warm one-line-touch rebuild** — touch one Rust source file in the crate the strategy routing
   lives in, then rebuild.

These three numbers are what PROJECT.md's tripwire 3 needs: the first says what a CI cold image
costs, the second says what the build system's overhead floor is, and the third says what the
actual edit loop feels like — which is the number that decides whether a Python-side change can be
iterated on quickly or whether every touch pays a compile.

Write `docs/adr/0002-rust-rebuild-time-tripwire.md` with the three numbers, the date, the machine
(CPU model, core count, RAM), the toolchain version, whether the cargo cache was warm, and the
exact command used for each. A measurement with no machine spec is not reproducible and cannot be
compared against the next one. State plainly whether the measured edit loop crosses the threshold
PROJECT.md's tripwire sets, and if it does, say so as a finding rather than softening it — the
tripwire exists to trigger a revisit, and a number that is quietly rounded down defeats it.

Write `docs/adr/0001-shelve-tenancy-patch.md` per D-05, carrying the defect evidence and file:line
citations that already exist in PROJECT.md's Key Decisions table rather than re-deriving them.
The ADR must state: which seams in the tenancy work were genuinely valuable and worth revisiting;
the specific defects that made the patch untenable, each with its `file:line` citation; the
decision to run one live node process per tenant so that isolation is a property of the process
boundary instead of a patch; and where the branch is preserved. Preserve it as an annotated tag
`archive/tenancy-768cbf3664` on the fork that backs the submodule, and record in the ADR the exact
command that restores it. `FOUND-03` is satisfied by the written record, not by the tag alone — a
tag with no explanation is a branch nobody will ever dare delete and nobody will ever read.

Create the `docs/adr/` directory as part of this task; it does not exist yet, and these two files
establish the numbering convention for every later ADR in the project.
