<objective>
Take the tracer's single-symbol, single-month loader to real breadth: the timestamp-unit boundary
handled per file, full available history per symbol, a handful of majors with genuinely different
listing dates, resumable verified ingestion, and the catalog moved into object storage.

Purpose: the roadmap names ingestion as the largest single cost in this phase, and RESEARCH.md
found the one thing that makes it dangerous rather than merely tedious — the bulk kline files
silently changed timestamp units at 2025-01-01 with no marker of any kind, so a loader written and
tested against 2024 data misdates every 2025 bar without ever raising. A full-history ingest for
any symbol listed before 2025 crosses that boundary.
Output: a loader that is correct across the boundary, idempotent on re-run, and writing into a
catalog both machines and CI read.
</objective>

  <action>
Extract the unit detection into a named `detect_timestamp_unit(raw_value)` that returns a
nanosecond multiplier from the digit count of the raw timestamp string — 13 digits are
milliseconds, 16 are microseconds. Detect it **per file**, not once per ingest and not from the
date in the filename: RESEARCH.md verified by live fetch that the two eras are byte-identical in
CSV shape, with no header change, no version marker and no filename change, so the digit count is
the only self-describing signal. A file published late as a historical backfill, or one spanning a
timezone boundary, is covered by digit-count detection and is not covered by a filename heuristic.
Raise on any digit count that is neither 13 nor 16, rather than guessing — an unexpected width is
a new upstream change and should stop the ingest loudly the way the last one should have.

Check the detected unit's consistency within a file and raise if rows disagree, so a mixed file
surfaces immediately rather than producing a sequence with one impossible jump in it.

Keep the close-time convention from D-24 and add the negative assertion: no bar's event timestamp
may equal its row's open-time value. The positive assertion alone passes for a symbol whose open
and close happen to be tested at a boundary where both look plausible; the negative one is what
catches a silent convention flip.

Add monthly-archive support alongside the daily archives the tracer used. Full available history
per symbol from its listing date (D-22) is thousands of daily files and dozens of monthly ones;
prefer monthly for the bulk and fall back to daily for the current partial month. Verify the
checksum sidecar for every archive of either kind.

Add `IngestLedger`: a small on-disk record of which archives have been downloaded and
checksum-verified, so re-running skips them. D-25 requires idempotent and resumable ingestion, and
a full-history multi-symbol ingest is long enough that it will be interrupted at least once. The
ledger records the archive name and its verified digest; a file is skipped only when both its
presence and its recorded digest match, so a truncated download is re-fetched rather than trusted.

Harden the extraction path: read entries by explicit member name into a controlled directory and
reject any entry whose resolved path escapes it. Never call a bulk extract-all on an archive
fetched over the network. On a checksum mismatch, remove any partially written output before
raising, so a subsequent run does not find and trust a half-file.

Check in four fixtures: a small millisecond-era CSV, a small microsecond-era CSV, a deliberately
corrupted archive, and its published-digest sidecar. Every parsing behavior above must be testable
with no network access, so the suite stays fast and stays green on a machine with no egress.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public bulk-data host → local filesystem | thousands of archives are downloaded and extracted |
| local process → object storage | catalog writes cross the network with cloud credentials |
| object storage → CI and both developer machines | the same bytes are read by three independent consumers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-26 | Tampering | archive extraction over a full-history ingest | high | mitigate | Entries are read by explicit member name into a controlled directory with an escape check; the module contains no bulk extract-all call, asserted by an acceptance criterion. Scale is what makes this matter — one bad entry in thousands of archives is easy to miss |
| T-01-27 | Tampering | resumable ingest ledger | high | mitigate | A file is skipped only when both its presence and its recorded verified digest match, so a truncated or replaced download is re-fetched rather than trusted on filename alone |
| T-01-28 | Tampering | silently misdated bars across the unit boundary | high | mitigate | Per-file digit-count detection, an intra-file consistency check, and a raise on any unexpected digit width; the negative assertion that no bar carries its open-time value catches a silent convention flip |
| T-01-29 | Information Disclosure | object-store credentials | medium | mitigate | Credentials come from the environment or the ambient cloud identity, never from a committed file; the catalog holds only public market data, so the exposure ceiling is write access rather than data secrecy |
| T-01-30 | Tampering | shared catalog writable by CI | medium | mitigate | CI is granted read-only on the bucket; only the developer identity writes. A CI job that could rewrite the catalog could silently change what every determinism test compares against |
| T-01-31 | Denial of Service | full-history download volume | low | accept | Four symbols of 1-hour bars is a bounded, one-time cost against a public host designed for bulk download; the ingest ledger means an interrupted run is never repeated from scratch |
</threat_model>
