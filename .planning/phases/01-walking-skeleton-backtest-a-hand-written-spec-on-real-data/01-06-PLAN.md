<objective>
Start the daily instrument-universe snapshot, on a schedule that runs whether or not anyone is at
a keyboard, storing the raw payload alongside extracted columns.

Purpose: the roadmap flags `DATA-03` as non-backfillable and cheap here, impossible later. Every
day this is not recording is a permanently missing row, and no amount of effort in Phase 2 or
Phase 3 can recover one. That is why this plan runs in the same wave as the tracer rather than
after it — the waiting period for success criterion 4's gapless daily count has to overlap the
rest of the phase's build, not follow it.
Output: a scheduled workflow writing one row per symbol per day into a hosted Postgres, with the
raw response preserved.
</objective>

  <context>
CONTEXT.md leaves this to discretion, but the consequence is not discretionary: this database is
about to start accumulating rows that cannot be regenerated for any day it misses. Moving the
history to a different provider later means a data export and import against a table that is the
sole record of the instrument universe on every past date. That makes the choice a one-way door
even though the technology behind it is ordinary.

The `apps/server/infra` CDK stack already in the repository is not used by this phase — D-12 puts
the cron on GitHub Actions — but it is the reference point for where the secrets manager of D-16
gets provisioned, and it biases the answer toward the AWS-native option if the rest of the
platform is heading there.
  </context>
  <decision>
Which hosted Postgres holds the non-backfillable snapshot history, and which secrets manager holds
its connection credential?
  </decision>
  <options>
**Option A — Neon + AWS Secrets Manager.**
  - Pro: a free tier that comfortably fits one small table growing by a few thousand rows a day;
    connection string works unchanged with the existing Prisma tooling.
  - Pro: no infrastructure to provision before the first cron can fire — the fastest path to the
    history actually starting.
  - Con: two vendors instead of one; the database sits outside whatever account the rest of the
    platform later lives in.

**Option B — Supabase + AWS Secrets Manager.**
  - Pro: same fast start as Neon, plus a built-in SQL console useful for eyeballing the gapless
    daily count that success criterion 4 asks for.
  - Con: the same two-vendor split, and a broader product surface than a single table needs.

**Option C — RDS + AWS Secrets Manager, provisioned through the existing CDK stack.**
  - Pro: one account, one identity model; the secrets manager and the database are native to each
    other, and the CDK stack that would own it already exists in the tree.
  - Pro: no migration later if the platform consolidates on AWS.
  - Con: slower to stand up, and it costs money from day one for a table that holds a few
    megabytes — the delay is the real cost, because it is a delay to the history starting.

**Recommendation: Option A.** The dominant risk in this requirement is not vendor choice, it is
elapsed days with no rows. Neon is the shortest path from this decision to the first row landing,
and if the platform later consolidates on AWS, one table's worth of history is an
export-and-import rather than a migration. Take C only if the secrets manager and account
structure are already provisioned and the delay is genuinely zero.
  </options>

  <action>
Create `engine/data/exchange_info.py`. `fetch_exchange_info()` calls the exchange's public
instrument-universe endpoint with no credentials — it is a public endpoint and Phase 1 holds no
keys — and first probes the exchange's liveness endpoint so a network failure is distinguishable
from an empty universe. Raise `SnapshotFetchError` on any non-200, on a body that does not parse,
or on a body whose shape does not carry a symbols collection. `extract_rows(payload)` returns one
record per symbol carrying the D-13 extracted columns, reading the tick size, step size and
minimum notional out of the per-symbol filter list and parsing each through `parse_money` so the
values are exact decimals. A symbol missing one of those filters gets an explicit null for that
column and is still recorded.

Store the raw response gzip-compressed in the raw payload column, alongside the extracted columns.
D-13 is explicit about why: the exchange adds filters over time, and a field not captured today is
permanently lost for every past day. The extracted columns are the query surface; the raw blob is
the insurance.

Create `engine/cli/snapshot.py` as the cron entry point. It resolves the connection string from
the secrets manager (falling back to the environment variable the workflow sets), fetches,
extracts, and writes every row through `record_snapshot` in one transaction. On any failure it
exits non-zero with the failure on stderr. A cron that exits zero having written nothing is
indistinguishable from a day the universe did not change, and D-14's whole no-dedup design exists
to make that distinction possible — so the entry point must never swallow an error.

Write one row per symbol every day unconditionally, even when byte-identical to yesterday. Add no
uniqueness constraint, no conflict clause, no valid-from/valid-to range, and no "skip if unchanged"
branch. This looks wasteful and is deliberate: a deduplicated table cannot tell "the universe did
not change" from "the cron silently died", which is exactly what success criterion 4's gapless
daily count is there to prove.

Copy a trimmed version of the real response fixture already present in the vendored checkout as
`engine/tests/data/fixtures/exchange_info_sample.json`, so extraction is unit-testable with no
network access. Cover all seven behaviors above.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public exchange REST → cron job | an untrusted JSON response is parsed and persisted |
| secrets manager → CI runner | the hosted database credential crosses into an ephemeral runner |
| CI runner → hosted Postgres | writes cross the public internet |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Information Disclosure | hosted connection string | high | mitigate | D-16 — the credential lives in a secrets manager and is surfaced to the job as a masked repository secret; no step echoes it, and no committed file contains it. Establishing this pattern now on a low-stakes credential is the point, so Phase 4's exchange keys inherit a working path rather than a migration |
| T-01-22 | Tampering | exchange response shape | medium | mitigate | The fetch raises on a non-200, an unparseable body, or a body missing the symbols collection, rather than extracting rows from garbage; the raw payload is stored so any later dispute is decidable against the original bytes |
| T-01-23 | Repudiation | silently dead cron | high | mitigate | No `continue-on-error`; a failed fetch or write exits non-zero and shows red. D-14's no-dedup rule plus the recorded gapless-count query make a dead day visible as a missing date rather than as an unchanged universe |
| T-01-24 | Tampering | SQL construction in the writer | high | mitigate | Writes go through the parameterized SQLAlchemy Core `record_snapshot` from plan 01-02; no statement is built by string interpolation |
| T-01-25 | Denial of Service | exchange rate limiting the cron | low | accept | One request per day against a public endpoint with generous limits; a rate-limit response surfaces as a failed run rather than as silent data loss, which is the outcome that matters here |
</threat_model>
