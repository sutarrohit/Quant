<objective>
Start the daily instrument-universe snapshot, on a schedule that runs whether or not anyone is at
a keyboard, storing the raw payload alongside extracted columns.

Purpose: the roadmap flags `DATA-03` as non-backfillable and cheap here, impossible later. Every
day this is not recording is a permanently missing row, and no amount of effort in Phase 2 or
Phase 3 can recover one. That is why this plan runs in the same wave as the tracer rather than
after it — the waiting period for success criterion 4's gapless daily count has to overlap the
rest of the phase's build, not follow it.
Output: a scheduled workflow writing one row per symbol per day into a hosted Postgres, with the
raw response preserved.
</objective>

  <action>
Create `engine/data/exchange_info.py`. `fetch_exchange_info()` calls the exchange's public
instrument-universe endpoint with no credentials — it is a public endpoint and Phase 1 holds no
keys — and first probes the exchange's liveness endpoint so a network failure is distinguishable
from an empty universe. Raise `SnapshotFetchError` on any non-200, on a body that does not parse,
or on a body whose shape does not carry a symbols collection. `extract_rows(payload)` returns one
record per symbol carrying the D-13 extracted columns, reading the tick size, step size and
minimum notional out of the per-symbol filter list and parsing each through `parse_money` so the
values are exact decimals. A symbol missing one of those filters gets an explicit null for that
column and is still recorded.

Store the raw response gzip-compressed in the raw payload column, alongside the extracted columns.
D-13 is explicit about why: the exchange adds filters over time, and a field not captured today is
permanently lost for every past day. The extracted columns are the query surface; the raw blob is
the insurance.

Create `engine/cli/snapshot.py` as the cron entry point. It resolves the connection string from
the secrets manager (falling back to the environment variable the workflow sets), fetches,
extracts, and writes the whole capture through `record_capture` in one transaction. On any failure
it exits non-zero with the failure on stderr. A cron that exits zero having written nothing is
indistinguishable from a day the universe did not change, and D-14's whole no-dedup design exists
to make that distinction possible — so the entry point must never swallow an error.

Compute the capture's identity before writing: `capture_date` is today's UTC calendar date,
`captured_at` is one `datetime` read once and passed in for every child row, `payload_sha256` is
the digest of the uncompressed response bytes, and `expected_symbol_count` is the length of the
symbols collection in the parsed payload. `record_capture` sets `actual_symbol_count` from what it
actually wrote and flips the parent to `complete` at the end of the transaction.

The parent row is what makes success criterion 4 checkable. The criterion claims *one complete
capture per day with no gaps*, and a table of per-symbol rows cannot support that claim: it cannot
tell a finished capture from one that died halfway, it cannot tell that yesterday recorded 400
symbols where today recorded 12, and after a retry it holds two interleaved sets with nothing
marking which is real. Reading one `captured_at` per statement makes it worse — a several-hundred
row batch spanning midnight lands one capture on two calendar dates.

Write one row per symbol every day unconditionally, even when byte-identical to yesterday. Add no
uniqueness constraint at either level, no conflict clause, no valid-from/valid-to range, and no
"skip if unchanged" branch. This looks wasteful and is deliberate: a deduplicated table cannot tell
"the universe did not change" from "the cron silently died", which is exactly what success
criterion 4's gapless daily count is there to prove. The same reasoning bars a unique constraint on
`capture_date` — it would make a retry fail rather than be visible, collapsing two facts into one
in exactly the way D-14 forbids on the child table.

Copy a trimmed version of the real response fixture already present in the vendored checkout as
`engine/tests/data/fixtures/exchange_info_sample.json`, so extraction is unit-testable with no
network access. Cover all seven behaviors above.

Write `.github/workflows/exchange-info-snapshot.yml`: a `schedule` cron trigger running once daily
at a fixed UTC time, plus a `workflow_dispatch` trigger so the first run can be forced immediately
rather than waiting a day. Set an explicit `timeout-minutes` and no `continue-on-error` anywhere —
a failed snapshot must show as a red run, because a green run that wrote nothing is the exact
failure mode this history cannot survive.

The job installs Python 3.13 and uv, then installs **only** what the snapshot path needs, with one
named mechanism rather than an approximation:
`uv sync --project engine --frozen --no-install-project --only-group snapshot`.

Every flag is load-bearing. `--only-group snapshot` selects the dependency group plan 01-03
declared in `engine/pyproject.toml` — the HTTP client, SQLAlchemy and the Postgres driver.
`--frozen` resolves it from the committed `engine/uv.lock`, so the daily job installs the same
pinned versions the rest of the project does; an explicit package list written into this YAML file
would drift from the lockfile the first time anything is bumped, and nothing would notice.
`--no-install-project` is what keeps the editable path dependency on the vendored engine — and
therefore the whole Rust compile measured in plan 01-03 — out of a job that runs every single day.
A daily job that takes that long to start is a daily job that someone paying for minutes eventually
disables, and this is the one history that cannot survive being disabled.

Because the project is not installed, invoke the entry point as a module from the repository root
so the flat-layout `engine` package resolves from the working directory. Assert in the job that the
*trading engine* package is not importable, so the exclusion cannot silently regress into a full
build. Add a job-level dependency cache keyed on the engine lockfile.

Read the connection string from the repository secret into the environment, and read nothing from
a committed file. Print no part of the connection string at any log level.

Trigger the workflow manually once, then confirm rows landed in the hosted store. Do not verify by
firing the workflow and sleeping: that assumes GitHub has already discovered the file, that the
branch carrying it is pushed, that the run finishes inside the sleep, and — worst — a `run list`
afterwards can happily report the conclusion of an *older* run and call it a pass. Capture the
newest run id before triggering, poll until a different id appears, then wait on that specific id
with a bounded timeout. The verify command below does exactly this.

Record in ADR-0004 the date and UTC time of the first successful run, because success criterion 4
is a claim about a start date and a count, and the start date has to be written down on the day it
happens. Add to the ADR the exact completeness query a reader can run later:
`SELECT capture_date, status, expected_symbol_count, actual_symbol_count FROM snapshot_capture ORDER BY capture_date`
— a missing date is a day the cron died, a row with `status <> 'complete'` is a capture that failed
partway, and a row whose actual count is below its expected count is a capture that lost symbols.
Add the child-side count alongside it,
`SELECT captured_at::date AS d, count(*) FROM symbol_listing_snapshot GROUP BY d ORDER BY d`, and
say in the ADR which of the two answers which question: the child count shows volume, the parent
table shows completeness, and only the second can support criterion 4's actual claim. The whole
no-dedup design of D-14 exists so that both queries can be trusted.

Note in the ADR that success criterion 4 cannot be satisfied on the day this merges: it is a claim
about consecutive days, so it needs elapsed calendar time. Shipping this in the same wave as the
tracer is what makes that waiting period overlap the rest of the phase instead of extending it.
