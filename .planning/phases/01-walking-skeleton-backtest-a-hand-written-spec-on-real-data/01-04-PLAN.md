<objective>
Make `schemas/strategy-spec.v1.json` the single source of truth for the strategy contract, wire
the two-language codegen pipeline behind it, and build the Python half of the float-in-money guard.

Purpose: `FOUND-04` says one schema, three languages, no drift; `FOUND-09` says a float reaching a
money field fails the build. RESEARCH.md found a real gap between those two: the documented
decimal path in the Python generator keys off `"type": "number"`, which is exactly the JSON wire
type D-07 forbids the TypeScript side from seeing. That gap is an open question, not a known
answer, and this plan opens with a spike whose output is a recorded decision rather than an
assumed mechanism.
Output: the versioned schema, a working generate step, a strict-Decimal money boundary, a guard
test that fails on a float, and TS/SQL guard stubs.
</objective>

Which mechanism converts the generated money field into a strict `Decimal` on the Python side,
while the TypeScript side keeps emitting `string`?
  </decision>
  <options>
**Option A — a hand-written wrapper module outside the generated file.** `engine/money.py` owns a
`parse_money()` that calls `Decimal(value)` on the known money-field names after generation.
  - Pro: the generated file stays untouched and regenerable; no generator internals depended on.
  - Pro: the conversion is one small, readable, testable file — the lazy option that works.
  - Con: the money-field name list is maintained by hand and can drift from the schema; needs a
    test that walks the schema and asserts every money-patterned field is in the list.

**Option B — a custom template directory passed to the generator.** The generator emits a
`field_validator` on the money fields directly.
  - Pro: no hand-maintained field list — the schema drives it end to end.
  - Con: couples the build to the generator's internal template structure, which is not a stable
    public contract; a generator upgrade can silently stop applying the validator.

**Option C — a custom base class the generated models inherit.** The base class carries the strict
config and a model validator that coerces pattern-matched string fields to `Decimal`.
  - Pro: uses a documented generator flag rather than template internals.
  - Pro: the strict config lives in one place and applies to every future generated model.
  - Con: the coercion rule has to identify money fields at runtime rather than from the schema.

**Recommendation if the spike shows no documented flag:** Option A, with the schema-walking drift
test that closes its single weakness. It is the smallest mechanism that satisfies both D-06 (schema
is authoritative) and D-07 (Python gets Decimal, TypeScript gets string), and it depends on no
generator internal. Only prefer B or C if the spike shows the generated output already carries a
usable hook.
  </options>

  <action>
Create `engine/money.py` exposing `MONEY_SCALE = 8` matching the schema pattern's maximum scale,
a strict Pydantic model `Money` with `model_config = ConfigDict(strict=True)` and a single
`Decimal` field, `parse_money(value)` returning a `Decimal` from a string or `Decimal` and raising
for anything else, `to_canonical_str(value)` producing the one canonical decimal-string form used
by every hash input, and `assert_no_floats(obj)` — a recursive walker that raises naming the path
where a `float` was found.

**Keep the wire boundary and the internal boundary separate, and test them separately.** These are
two different contracts and one strict model cannot hold both:

- **Wire** — a money value arriving from JSON, from a spec file, or from a CSV row is a decimal
  *string*. `parse_money` is the only sanctioned way it becomes a `Decimal`: it accepts a string
  matching the schema's pattern (or an existing `Decimal`, idempotently) and raises on everything
  else, including a `float`, an empty string and `None`.
- **Internal** — once inside the system a money value is a `Decimal` and nothing else.
  `ConfigDict(strict=True)` on `Money` is what enforces that, and it means `Money` rejects a
  string in Python mode. That rejection is the contract working, not a bug to route around.

Do not build the wire path on Pydantic's JSON-mode validation entry point, or on any assumption
about which input types strict mode permits in JSON mode — that is a version-dependent detail of
the conversion table, and pinning the project's money contract to it would make a library upgrade a
